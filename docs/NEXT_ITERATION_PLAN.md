## 跨群接入专项 A01：用户身份授权读取

### 目标和已知边界

目标是减少大量工作群逐一加入机器人的操作，服务个人跨群工作汇总。当前 0.3.0 仅实现应用身份：同一个“拾光工作汇报”机器人加入多个目标群，共用应用凭据和权限，不是每群创建新应用。登录飞书客户端不会自动将个人群消息权限授予本程序。

官方历史消息接口列有 `user_access_token` 及 `im:message.group_msg:get_as_user` 等用户身份权限，官方 CLI 也区分用户与机器人身份。但历史消息文档的前提仍列有机器人入群要求，因此**用户身份能否在本组织免机器人入群读取目标群，属于待验证问题，尚无本工程实测结论**。不能承诺一次登录读取所有群，也不能据此推定外部群、保密群或全部历史都可访问。

资料依据（2026-10-24 查阅）：[官方历史消息接口](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/list)、[官方 CLI 身份说明](https://github.com/larksuite/cli/blob/main/skills/lark-im/SKILL.md#identity-and-token-mapping)、[群列表说明](https://github.com/larksuite/cli/blob/main/skills/lark-im/references/lark-im-chat-list.md)。实施时应重新核对当时的权限和应用支持条件。

### 分阶段交付

1. **先核对条件：**本组织是否可申请所需用户身份只读权限，管理员审批与应用类型限制，授权和回调方式是否适用于本机部署；只申请读取及维持授权实际需要的范围。
2. **再做最小实测：**以本人授权，在机器人已加入及未加入的少量指定内部群对照群列表、时间范围和历史消息结果；完整保留分页、业务错误及覆盖结论，验证重点为未入机器人群。
3. **形成决策记录：**若未入机器人群可读，明确适用组织、群类型、本人可见历史和限制；若只能看到群但不能读取消息，不能记为接入成功；若不支持或权限不可用，记录原因并保留现有逐群加机器人的方式。
4. **验证通过后再设计改造：**在现有程序增加可选的用户授权模式，用户选定相关群与日期后才同步；保留应用身份模式作为兼容路径，继续复用报告、快照与审阅流程。

### 必须补充的设计及验收

- **授权生命周期：**登录、授权、刷新、到期、撤销及重新授权的状态与失败恢复；页面清楚显示当前授权账号和组织，客户端登录状态不能冒充程序授权成功。
- **身份与可见范围：**区分应用身份、用户身份及组织；群列表可见不等于消息可读。用户模式默认只同步明确勾选的群，不自动全量读取本人所有会话。
- **材料隔离：**缓存、本人标识、常用设置及报告需识别所属身份和组织；不能沿用另一身份的缓存来冒充本次读取成功；原报告和姓名快照保持原样。
- **令牌保存：**令牌仅由本机服务端管理，页面、普通操作记录和报告不返回令牌；断开授权后停止后续读取，已存消息与报告的保留方式由用户明确选择。具体安全存储和备份规则在实现前确定。
- **边界对照：**检查机器人未加入群、本人不可访问群、跨组织或外部群、保密或禁止复制群、分页及历史可见时间限制；不支持的范围明确说明，不绕过群或组织访问限制。
- **交付证据：**分别给出列群、读消息、刷新授权及撤销后的结果；仅将实际成功读取并核对的群与时间写为验证通过。

本次仅记录专项，未开通权限、实施个人授权、安装 CLI 或修改现有接入。新增接入能力不属于 M09／M10 框架扩展，也不将原第 15 项同步优化改称用户授权。

## 需要先定下的产品设计

### 1. 页面层级与表单

推荐保留现有主工作台，不重做整个站点：

- 主工作台：消息范围、周期、汇报视角和用途。
- 配置页／弹窗：先列当前用途关键材料，选填背景、论证条件和章节设置折叠展示。
- 预览区：正文、材料缺项、来源覆盖和人工陈述可核对；保留“明确保存后再按条审阅”的当前顺序。
- 草稿入口：继续未完成内容；不与正式汇报记录混列。
- 历史记录：检索、版本链和对照；草稿恢复不创建报告。

接收对象、背景熟悉程度等字段已经存在，下一步是改善填写与复用体验。改变用途时只对适用字段提供明确的保留／清理选择，不能把旧建议和旧承诺直接带入新主题。

### 2. 草稿、偏好、候选、已存报告

四者分开：

| 对象 | 内容 | 保存和恢复原则 |
| --- | --- | --- |
| 用途偏好 | 模板、框架、排序等通用选择 | 延续当前规则，不包含本次业务材料 |
| 本机草稿 | 未完成的配置和人工材料，后续包括编辑内容 | 独立本机存储，显示更新时间；按来源、工作范围、编辑模式及原报告隔离；可主动放弃 |
| 候选预览 | 某次事实、配置和正文的临时快照 | 延续当前有效期；恢复输入不等于恢复旧候选，过期后重新预览并核对 |
| 已存报告 | 正文、证据、配置定义及版本快照 | 保持不可覆盖的历史；编辑另存，恢复草稿不修改旧稿 |

建议使用现有 SQLite 存独立草稿，保存版本号用于检查多标签并发覆盖。先实现用途材料的完整恢复路径，再扩展两类报告编辑，避免一次改动所有编辑器。草稿容量上限、清理和备份恢复规则需在实现前写入契约；不以“材料进入常用设置”代替草稿能力。

### 3. 核对状态

已有的待补充提示与来源检查应集中展示，先做可确定的规则检查：字段缺失、范围覆盖、引用存在性、作者归属、被排除支撑等。金额、根因、收益和里程碑真伪没有充分依据时提示人工核对，不提供虚假的综合可信分数。

需要区分“草稿”“使用者已核对”“材料仍不完整”。“使用者已核对”只记录本机审阅动作，不意味着对方批准、外部事实认证或工作已经验收通过；审阅后再修改正文或关键材料应提示重新核对。

### 4. 周期报告与专题稿

日报／周报／月报继续按周期总结工作。RIDE 是一个具体方案的取舍说明，AAR 围绕一个具体事件；它们需要专题名称和证据时间范围，不应被迫使用“某日工作日报”标题。

最小设计先复用现有入口，把专题名称与所选统计范围分别显示；RIDE／AAR 作为重点专题说明，下面保留事实及证据。先不新增独立专题工作台，任意事件时间区间、无群消息的纯人工专题留待真实需要明确后再设计。已有流程中的专题证据仍只能来自明确选中的群、时间和成员范围，不引入多轮工具 Agent 或完整项目管理平台。

RIDE 沿用既有调研约定：Risk—Interest—Difference—Effect，页面 E 明确为“代价、限制与副作用”；保存定义版本。方案比较对象、收益条件、采用成本和不确定性需明确，不能自动编造数值或对方关切。AAR 的原因先作为人工分析／待验证假设，改进动作至少明确责任人和检查点。

### 5. 项目上下文与目标基线

目前项目视角以所选群作为范围，已有项目状态、里程碑、依赖等人工字段。若试用证明每次重复填写负担明显，再设计轻量项目档案：项目名称、默认群、默认接收对象、人工确认的目标及时间基线；本次生成前显示引用了哪版背景，允许覆盖。

群与项目的关系需明确：一个群可能讨论多个项目。首版仅人工选择与备注，不自动判定消息所属项目；没有目标基线、实际值和单位时不计算达成率。

### 6. 改进行动的闭环

已有“事项时间线”是人工关联相关消息，不是完整的行动台账。AAR 首版先在报告中保存行动、负责人和检查点。真实出现跨报告跟踪需求后，再增加轻量行动记录及人工状态确认；不能仅凭截止日期已到或后续沉默自动标为完成。

## 成本与验收约束

任务 1—7 优先复用现有 Python、SQLite、原生页面和飞书权限。A01 可能涉及新增用户身份权限和本机授权流程，先验证可行性再评估改造成本，不视为现有权限自然覆盖。没有证明收益前，不增加向量数据库、完整项目管理系统、额外消息平台或收费模型依赖。

每一批按实际变更运行针对性检查及必要回归，保存页面验收证据；涉及库结构时迁移前备份并核对既有报告、证据和姓名设置。真实试用与自动化检查分开记录，框架数量不作为质量指标。
